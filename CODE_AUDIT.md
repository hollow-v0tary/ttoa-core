# THAOS — аудит структуры исходного проекта

## Статус

Стабилизирована **статическая Lite-сборка** без миграции пользовательских данных. Проект пока не является полностью структурированной CMS: задача на данный этап — безопасная публикация и честная проверка функциональности.

## Что проверено и улучшено

| Область | Было | Lite Stable |
|---|---|---|
| Переходы | Ранее использовались текстовый экран и «Пепельная вуаль» | В актуальной сборке убраны: переходы между страницами мгновенные |
| Фоновая анимация | Кадры генерировались и в скрытых вкладках | Приостановка при переключении вкладки |
| Core | Неиспользуемый `core-modules.js` на 7 модулей при 8 действующих | Удалён неиспользуемый файл; рабочие отдельные HTML-руководства сохранены |
| CMS | Модули в меню редактора не совпадали по порядку с карточками | Порядок унифицирован |
| Роли | Привилегированный редактор именовался «Мастер» | UI использует «Редактор», без изменения защищённого ключа Firestore `siteAdmins` |
| Сессия | В браузере использовалась стандартная Firebase persistence | При авторизации явно запрашивается `browserLocalPersistence` |
| Данные | `classes.json` выглядит как каталог, но является заглушкой | Это явно задокументировано; действующие `class-data.js` и `path-descriptions.js` не сломаны |
| Навигация | Ранее использовался JS-перехват ссылок | Теперь обычные ссылки работают нативно; переключатели классов и рас вызывают `location.assign()` |

## Источники данных, которые пока разделены

- `js/class-data.js`: каталог 13 базовых классов.
- `js/path-descriptions.js`: пути и их описания.
- `js/race-data.js`: каталог 12 рас.
- `js/world-data.js`: 25 территорий (23 точки на карте), 5 государств, легенды, праздники и правление.
- `data/world-lore.json`: редакторская копия части `world-data.js`, не runtime-сервис.
- `js/player-app.js`: логика персонажей/групп + Firebase.
- `js/cms-manifest.js`, `js/cms-public.js`, `js/admin.js`: редактирование **существующих** записей через Firestore.

## Главные ограничения, к которым нужно вернуться перед полноценным Editor/GM

1. Сделать версионируемый контентный контракт (`schemaVersion`, постоянные идентификаторы классов/навыков/путей) и валидаторы, затем переходить к созданию новых сущностей.
2. Не менять старые `classId`, `raceId`, `pathIndex` и сохранённые списки навыков без продуманной миграции: иначе уже созданные персонажи могут потерять корректные ссылки.
3. Увести структурные данные из разбросанных JS-каталогов в единые схемы, но только вместе с обновлением чтения во всех трёх клиентах (Codex/Editor/Player).
4. CMS сейчас патчит текст глав по порядковым `b0`, `b1`... и может переопределять обновлённые исходники при добавлении нового абзаца. Для будущего конструктора нужны **стабильные ID блоков**, черновики и история версий.
5. Разграничить глобального **Редактора** и **Мастера своей кампании**; обычный GM не должен получать запись в `siteAdmins`. Новая роль и права GM ещё **не реализованы**.
6. `Firestore`/`Storage` должны проверять право записи серверными правилами, а не только скрывать кнопки в интерфейсе. Текущие Rules сознательно не упрощены.
7. Проверить UI на опубликованном HTTPS-сайте и живом Firebase. Статические проверки не заменяют end-to-end тест авторизации и публикаций.

## Выполненные тесты

- `node --check` для всех `.js` — синтаксис проходит.
- `python tests/check_site.py` — 23 HTML, локальные ресурсы, важные CSS media rules, 5 государств и 26 праздников.
- `node tests/check_navigation.js` — отсутствие экранной анимации и мгновенное переключение классов/рас.
- Исходные арты 13 классов и 12 рас существуют; картинки модулей присутствуют.

В текущей среде Chromium возвращает `ERR_BLOCKED_BY_ADMINISTRATOR` даже для локального HTTP и `file://`, поэтому **реальный рендеринг браузера и работу Firebase в онлайне проверить здесь не удалось**. Для этого в `DEPLOY_FIRST.md` дан отдельный чеклист.
